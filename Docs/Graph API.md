# Graph API: first execution flow contract

This document defines the current contract for Blueprint graph connections and synchronous flow execution. The C++ graph model identifies flow pins with `EPinRole::Flow`, and `BlueprintGraph::Execute` validates and runs flow paths.

## Scope

The first sample is `Start → Print Message("Hello from my workflow") → End`. Links in this slice carry control flow only: they select which node executes next and carry no values. `Print Message` owns its configured string. General typed data pins, conversions, branches, loops, async execution, and cancellation are out of scope.

## Flow link

A flow link connects an output pin on one node to an input pin on another. A link is valid only when both endpoint pins and their owning nodes exist in the same graph, the source pin is an output, and the destination pin is an input. Direction is source-to-destination; reverse-oriented and self-node links are invalid. Pin role must be explicit in node/pin metadata (or an equivalent flow marker); pin direction alone does not identify a flow pin. A graph may also contain data links; they are not traversed as control flow. Do not infer data types from pin names or add a general typed-pin framework for this slice.

Connection compatibility and cardinality are pin policies. `GraphPin::AllowConnectionWith(other)` decides whether a pin accepts a connection to the other pin, and `GraphPin::AllowMultipleConnections()` decides whether it may participate in multiple links. `GraphView::AddConnection` checks both endpoint policies and rejects a proposed connection that either endpoint disallows. The default policies permit multiple connections and require matching roles; flow pins override cardinality so outputs allow one connection while inputs allow many. Data pins keep their own compatibility and cardinality policy. Do not apply flow cardinality rules to data pins: for example, a data output may fan out to multiple compatible consumers.

Control-flow execution follows flow pins only. Each flow output has at most one successor, while a flow input may receive multiple links, allowing paths from different Start nodes to converge. Execution selects the unique outgoing link from the current node's flow output; it never chooses among competing outgoing links.

## Entry and termination

A runnable graph contains one or more Start nodes. Each Start is an independent entry point and its reachable flow path is executed separately, synchronously. A Start accepts no incoming flow links and must have exactly one outgoing flow link. End has no outgoing flow links and completes that path successfully when reached. The sample remains Start → Print Message → End. Reaching a node already visited within a path or exceeding the finite execution step limit is an execution error; looping semantics are not defined.

`BlueprintGraph::Execute` orders Starts by ascending `NodeId`. It validates the complete graph structure and every connection, pin owner/key/role, compatibility policy, and endpoint cardinality before invoking any node behavior, so malformed later paths cannot be discovered after earlier side effects. Once validation succeeds, Starts run sequentially and fail fast on the first runtime failure. Each path gets its own visited set and step limit (1024 executed nodes by default); `StepsExecuted` is aggregate, and each `StartResult` reports its Start ID, whether it executed, its success, path step count, and diagnostic. Starts after a runtime failure remain present with `Executed == false`. A graph with no Starts fails validation. If paths converge, shared downstream nodes execute once for each Start path that reaches them.

## Validation and errors

Validate the graph structure and all links before invoking behavior. Reject a Start without exactly one outgoing flow link or with incoming flow; any flow output pin with multiple links; empty or duplicate per-node pin keys; invalid ownership, endpoint, direction, role, compatibility, or cardinality; and outgoing flow links on End. Do not precompute a path: an unconnected branch output can be valid until selected. At runtime resolve only the selected output; an invalid or selected-but-unconnected output, a cycle, node failure, or step-limit breach fails that path. Reaching End or an explicit terminal completion succeeds. Data links do not determine control-flow traversal.

Unreachable non-Start nodes need not execute. The validator may report them as warnings, but they do not alter the first slice's execution result. Whether unreachable nodes should become hard validation errors is deferred until authoring requirements demand it.

## Implementation note

`GraphPin` stores input/output direction, an explicit `EPinRole` (`Data` or `Flow`), a stable `PinKey`, and connections by generated ID. Its virtual `AllowMultipleConnections` and `AllowConnectionWith` methods define connection policy. `GraphView::AddConnection` consults both endpoint policies. Blueprint flow output pins allow one connection each; flow inputs allow many. Start and End use dedicated node classes. `BlueprintNode::ExecuteFlow` returns a structured outcome: failure with diagnostic, continuation with a selected flow output key, or terminal completion. Its default implementation calls the existing `Execute()` virtual and selects the first existing flow output, preserving linear node behavior. Branch nodes override `ExecuteFlow` to select an output based on their own decision logic. The executor resolves that key after behavior returns, then continues dynamically. The configurable finite step limit defaults to 1024 executed nodes, including Start and End. The Start context-menu shortcut delegates to this graph executor.

This API remains control-flow only; data pins have independent policies and this task does not define data value transfer.

## Graph document persistence (NE-M1-02)

`GraphView` implements ARC's `ResourceManagement::Serialization::ISerializationInterface`. Its `Save` and `Load` methods use the shared `Serialzer_t` JSON archive, so callers can use ARC's `SaveToFile` and `LoadFromFile` helpers. The registry assigns the registered graph key to each `GraphView` when it creates the instance. Save/load use that stored key directly and compare it with the document's `graph_type`; they do not infer the graph type by scanning factories or relying on RTTI. `SaveDocument(graphType)` returns deterministic schema-v1 JSON; `LoadDocument(document, graphType, diagnostic)` validates the complete document and reconstructed factory pins before replacing graph contents. Graph and node registry keys identify definitions. `GraphNode::DocumentId` is a graph-scoped monotonic ID distinct from runtime `NodeId`; node definitions assign explicit `GraphPin::PinKey` values independent of `Name` and `PinId`. The Blueprint `Print Message` node stores a non-default authored message in `properties.message` and recreates its default from its factory. Load does not call `BlueprintGraph::Execute`, so incomplete graphs remain loadable. The `ISerializationInterface::Save` callback is void; save validation errors are available through `GetPersistenceDiagnostic()`. Branch runtime remains outside this API.

## Pin identity and branch execution (NE-M3-06)

Persisted pin identity must be a stable key declared by the node definition, separate from the visible pin label and the current vector-index `PinId`. Keys are unique within a node across inputs and outputs. For example, an action node can use `exec.in` and `exec.out`; a branch can use `exec.in`, `condition.true`, and `condition.false`. Connection records identify the node instance and pin key. Endpoint position determines direction: `from` resolves to an output and `to` to an input. The loader accepts legacy records with an explicit direction field only when it agrees with that endpoint position.

The executor follows the stable flow output `PinKey` returned by each node, while keeping schema version 1 unchanged. Each output has at most one link; a flow input may accept several links so independent Starts and branches can converge. The full graph structure, all links, endpoint ownership/roles, pin keys, compatibility, and cardinality are checked before behavior. Runtime traversal then tracks cycles and the 1024-step limit independently per Start path. A selected key must name a flow output on the executing node and that output must be connected. Unselected outputs may remain unconnected. Existing linear nodes use the default adapter from successful `Execute()` to their existing flow output. End stays terminal success. Branch condition/value semantics remain out of scope.
